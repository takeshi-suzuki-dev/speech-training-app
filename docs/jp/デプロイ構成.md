# デプロイ構成

フロントエンドとバックエンドをどちらもコンテナとして AWS ECS/Fargate 上で動かし、1つの Application Load Balancer の背後に配置している。HTTPS は前段の CloudFront で終端する。

公開URL: https://d22r3g893vf4i5.cloudfront.net

---

## リクエストの流れ

```
ブラウザ
  │ HTTPS
  ▼
CloudFront  (TLS終端、HTTPからのリダイレクト)
  │ HTTP
  ▼
Application Load Balancer
  ├── /api/*  ──►  Fargateタスク: Spring Boot (8080番)
  └── /*      ──►  Fargateタスク: Next.js standalone (3000番)
                        │
                        ▼
        Supabase PostgreSQL / Supabase Storage
        Azure AI Speech / ElevenLabs
```

## 構成リソース

| レイヤー             | リソース                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| レジストリ           | ECR: `cadence-backend`, `cadence-frontend`                                                      |
| オーケストレーション | ECSクラスター `cadence-cluster`、サービス `cadence-backend-svc`, `cadence-frontend-svc`         |
| ロードバランシング   | ALB `cadence-alb`、ターゲットグループ `cadence-backend-tg` (8080), `cadence-frontend-tg` (3000) |
| CDN / TLS            | ALB を配信元とする CloudFront ディストリビューション                                            |
| シークレット         | Secrets Manager: `cadence/backend`, `cadence/firebase-service-account`                          |

リージョンは `ap-northeast-1`。運用手順は [`infra/DEPLOY.md`](../../infra/DEPLOY.md) にある。

## ネットワーク

セキュリティグループを2つ用意し、IPアドレス範囲ではなく互いを参照させている。

- ALB用: インターネットから 80番 を受ける
- タスク用: **ALB用セキュリティグループからのみ** 8080番と3000番を受ける

Fargate タスクのIPはデプロイごとに変わるため、IPベースの指定は不安定であり、かつ許可範囲が広すぎる。ALBのセキュリティグループを参照させることで、ロードバランサーを通過した通信だけがタスクに到達する。

タスクはパブリックサブネットに置き、`assignPublicIp=ENABLED` としている。定石はプライベートサブネットと NAT Gateway の組み合わせだが、NAT Gateway の月額はこのスタック全体の費用を上回る。タスクが必要とする外向き通信はイメージの取得と外部API呼び出しだけなので、この構成を選んだ。

## シークレットの扱い

7つの値をタスク起動時に注入している。タスク定義では `environment` ではなく `secrets` ブロックを使うため、値がコンソールのタスク定義画面に表示されることはない。

`cadence/backend` にアプリケーションの6つの値をJSONとしてまとめ、個別のキーはARNの末尾に `:キー名::` を付けて参照する。Firebase のサービスアカウントJSONは別のシークレットとして保管し、値全体をそのまま注入している。JSONの中にJSONを入れるとエスケープの誤りを招きやすいため、意図的に分離した。

ECS が注入できるのは環境変数だけである一方、Firebase Admin SDK の `GoogleCredentials.getApplicationDefault()` はファイルパスを要求する。この差を埋めるため、`FirebaseConfig` は `FIREBASE_CREDENTIALS_JSON` が設定されていればその文字列から読み込み、空であれば従来のファイル方式にフォールバックする。ローカル開発の手順を変えずに済ませるための構造である。

## 設計上の判断

**App Runner ではなく ECS/Fargate を選んだ。** App Runner の方が構築は速いが、ロードバランサー、ネットワーク、タスクのライフサイクルが隠蔽される。理解しておく価値があり、また説明できるようにしておきたい部分がそこにあるため、あえて ECS を選択した。

**ホストを分けず、1つのALBでパスによって振り分けている。** フロントエンドとAPIを同一オリジンで配信することで、本番環境からクロスオリジン通信そのものをなくし、ロードバランサーも1つに収めている。

**独自ドメインを取得せず、CloudFront で HTTPS 化した。** Firebase 認証は HTTPS を要求し、HTTPS のページから HTTP のAPIを呼ぶとブラウザが遮断する。ALB に ACM 証明書を付ける方法はドメインが前提になるが、CloudFront は自身のドメインに対する証明書を無償で提供する。

**API のベースURLを相対パスにした。** `NEXT_PUBLIC_*` はビルド時にバンドルへ埋め込まれるため、絶対URLを指定するとイメージが特定の環境に固定され、ドメインが変わるたびに再ビルドが必要になる。`NEXT_PUBLIC_API_BASE_URL` を空にしてビルドすると `/api/...` という相対パスになり、そのページを配信しているオリジンに対して解決される。

**HikariCP のプールサイズを5に制限した。** Supabase の無料プランのプーラーはセッションモードで15クライアントまでを許容する。HikariCP の既定値は10で、ローリングデプロイでは旧タスクと新タスクが同時に動くため、既定のままでは上限を超えて新タスクが起動できなかった。

## 遭遇した問題

**同一オリジンのPOSTでもCORSが働く。** ブラウザはGET以外のリクエストに、同一オリジンであっても `Origin` ヘッダーを付与し、CloudFront はそれを転送する。Spring は許可リストにないオリジンと判断し、`403 Invalid CORS request` を返していた。GETは対象外なのでカテゴリ一覧は表示され、見本音声の生成と採点だけが失敗するという症状になった。許可オリジンは `CORS_ALLOWED_ORIGINS` から与える形に変更した。

**履歴が端末に紐づき、かつ認可が欠けていた。** `training_attempts` はブラウザで生成して `localStorage` に保存したUUID (`client_id`) をキーにしており、その値をリクエストパラメータとして受け取ったうえで、呼び出し元本人のものかを検証していなかった。認証を通った利用者であれば他人のIDを指定して他人の履歴を読めてしまい、また同一の利用者でも別の端末では履歴が見えなかった。現在はカラム名を `user_id` に改め、認証済みの Firebase UID から `UUID.nameUUIDFromBytes` で導出している。同じ利用者からは常に同じUUIDが得られるため、スキーマ変更もセッション管理も不要である。

**`latest` タグは古いデプロイを隠す。** ローカルで修正を確認したものの、再ビルドしたイメージをpushしていなかったため、ECS は以前のイメージを取得し続け、修正が効いていないように見えた。コミットハッシュをタグにすればこの誤りは起こり得ない。それを導入するまでは、pushと `--force-new-deployment` を一連の操作として扱う。
